# Repository Guidelines

> **Editing note:** `CLAUDE.md` is a symlink to this file (`AGENTS.md`). Edit `AGENTS.md` — writes to `CLAUDE.md` are refused as symlink writes.

## Project Structure & Module Organization
- Runtime Python packages live under `src/`, grouped by feature (`src/tasks`, `src/projects`, etc.).
- Shared utilities (config loader, HTTP client, concurrency helpers) live in `src/lib/` and are imported by feature modules.
- CLI entrypoints and orchestration scripts sit in `scripts/`, keeping business logic inside `src/`.
- Mirror the `src/` layout inside `tests/` two levels deep so every module has a neighboring test.
- Ignore build artifacts (`__pycache__/`, `*.pyc`, local SQLite files) and local environment files via `.gitignore`.

## Build, Test, and Development Commands
- Standardize on CPython 3.11+ using a project-local virtual environment (`python3 -m venv .venv`).
- Use `python3` consistently in commands, scripts, and README examples unless you are referring to a language name or a literal code snippet.
- On macOS, activate the virtual environment with `source .venv/bin/activate`.
- Do not assume `python` exists or maps to the intended interpreter.
- Only the Python standard library is allowed; document any exception in advance. (Multi-tab `.xlsx` output is produced by the dependency-free `src/lib/xlsx_writer.py`, which hand-writes OOXML via `zipfile` — no third-party package required.)
- Run `python3 -m unittest discover tests` for the full test suite; use `python3 -m trace --count --file trace.out -m unittest discover tests` to check coverage when needed.
- Run the full test suite before committing non-trivial changes.
- Scripts that perform concurrent API fetches should expose a `--workers` override (see `get_tasks.py`, `get_task_extras.py`, `get_project_status_updates.py`); single-request and export/diagnostic scripts (e.g. `get_projects.py`, `export_users.py`, `inspect_project_status_data.py`) do not need one. Every script must respect the resolved `skip_ssl_verification` setting from the shared credential loader.
- Document every new CLI script (purpose, inputs, outputs) in the matching `docs/` reference file (`docs/sync-commands.md`, `docs/reports.md`, or `docs/jira-integration.md`) and add a one-line index entry below.
- Rebuild `tasks.hierarchy_depth` with `python3 -m scripts.backfill_task_hierarchy_depth` after schema changes; top-level tasks sit at depth 0 and each subtask increments by 1.

## Interactive CLI
- `scripts/interactive_cli.py` is a thin orchestrator over the standalone script `main()`s — it never reimplements business logic, it builds an `argv` list and calls the script's `main(argv)` via `run_script`. Every script stays independently runnable; the CLI is just a guided front end.
- Structure: `main()` shows 7 lifecycle categories, built by `build_top_menu(log_level)` and phase-specific `build_<phase>_menu` functions: **Client & Environment**, **Discover & Refresh Asana**, **Prepare Jira**, **Assess & Plan Migration**, **Migrate Projects**, **Maintain & Validate**, and **Advanced & Recovery**. Guided workflows preserve refresh/migration prerequisite order while delegating to existing script `main()` functions. The older technical menus remain reachable under Advanced & Recovery during the transition.
- Session state: a module-level `CliSession` (`_session`, set in `main()`) holds the active profile (`env_path`, `client_name`), per-profile `db_path`, configured Jira sites, current site, and persisted default site. `print_session_header()` renders the selected named site above the top menu. `append_jira_env_flag` appends `--jira-site <key>` (no per-command prompt). `_set_session` rebuilds it and exports `ASANA_JIRA_DB_PATH` plus `ASANA_JIRA_SITE_KEY` so in-process scripts target the active profile DB and site; switching a profile loads that profile's `JIRA_DEFAULT_SITE`. The Client & Environment menu can select a site for the session or persist a new default. On startup `main()` runs `run_startup_migration` once, which calls `config.migrate_home_profiles_into_project` to relocate any legacy `~/.asana_jira_env*` files into `profiles/` and re-key their Keychain secrets.
- Per-item pattern: a handler does `run_script(<module>.main, args_<thing>(log_level))`. The `args_*` builders assemble the `argv` list and own all interactive prompts; `build_common_args` seeds `--log-level`.
- Scope selection reuses fuzzy SQLite lookups over the active profile's database (`active_db_path()`): `_prompt_project_gid_from_lookup`, `_prompt_team_gid_from_lookup`, `_prompt_user_gid_from_lookup` (built on `_fuzzy_projects`/`_fuzzy_teams`/`_fuzzy_users`). Prefer these for any new project/team/user picker instead of writing a new prompt.
- Interactive input-file pickers scan the project-local `inputs/` directory (git-ignored except for `.gitkeep`) for `.txt`, `.csv`, and `.list` files; typed relative paths also resolve from `inputs/`.
- Team/project scope is deliberately prompted per operation rather than stored in `CliSession`, because operators commonly move between teams and projects during a migration. `show_migration_readiness` is a read-only, workspace-level advisory summary; scoped reports remain the source for project-level review.
- To add a script to the CLI: (1) import its `main` in the `from scripts import (...)` block, (2) write an `args_<thing>(log_level)` builder (reuse the lookup helpers + `prompt`/`confirm`), (3) add a `MenuItem` to the relevant `build_*_menu`. No need to re-investigate the file each time — follow this pattern.

## Coding Style & Naming Conventions
- Follow PEP 8 with 4-space indentation and descriptive snake_case module/function names.
- Prefer dataclasses and type hints (PEP 484 / `typing`) to keep data structures explicit.
- Keep each module focused on a single responsibility; expose a single public entrypoint per file and treat helpers as internal.
- Configuration and credentials are loaded from the resolved env file via `src/lib/config.py` (`load_credentials`); document any new setting in the README and env-file setup guidance. The two secret tokens (`ASANA_TOKEN`, `ATLASSIAN_TOKEN`) are stored in the macOS Keychain via `src/lib/keychain.py` (stdlib wrapper over the `security` CLI) when available — namespaced by profile slug (`keychain.account_for_slug`, e.g. `acme:ASANA_TOKEN`, `default:…` for the default profile; `legacy_account_for` reads pre-migration basename entries) — with read precedence process env → Keychain → env file and an automatic fallback to the env file off macOS; non-secret config always stays in the env file. `write_credentials_file` / `migrate_tokens_to_keychain` keep the two backends in sync.
- Profiles: a profile is a project-local non-secret config file at `profiles/<slug>.env` (`profiles/default.env` for the default profile). `CLIENT_NAME` is the display name; `config.slugify` derives the slug (the reserved value `default` is remapped to `default-client`) and `config.profile_slug` maps a profile/legacy filename back to a slug. The active profile is named by the `profiles/.asana_jira_active` marker (`config.read_active_slug` / `write_active_slug` / `has_active_marker`; the old root marker remains readable for compatibility); `_resolve_env_path` order is `ASANA_JIRA_ENV_FILE` → active marker → `profiles/default.env` → legacy `.asana_jira_env_path` pointer → `~/.asana_jira_env`. `config.list_project_profiles` discovers project profiles; `migrate_home_profiles_into_project` relocates legacy `~/.asana_jira_env*` files (still discovered via `list_credential_profiles`) and re-keys their Keychain entries. `project_profile_path` / `project_profiles_dir` build paths; `read_profile_name` / `read_profile_jira_urls` read display values. Each profile gets its own database — `data/asana_<slug>.sqlite` (the default profile keeps `data/asana.sqlite`). `database.resolve_default_db_path()` resolves the DB path as `ASANA_JIRA_DB_PATH` env override → caller fallback (a script's own `DEFAULT_DB_PATH`) → module default; `Database(db_path=None)` uses it. Scripts accepting `--database` default it to `resolve_default_db_path()`. `profiles/` (including its active marker) is git-ignored.

## Testing Guidelines
- Write unit tests under `tests/unit` and integration specs under `tests/integration`, naming files `<subject>.test.py`.
- Keep custom fixtures and mocks alongside tests (e.g., `tests/unit/__mocks__/`).
- Target ≥90% statement coverage; include asynchronous and pagination edge cases in every suite.
- Use `python3 -m unittest --failfast` during development for faster feedback and add regression tests for every bug fix.

## Commit Guidelines
- Follow Conventional Commits (e.g., `feat(tasks): add recurring scheduling`). Scope names should align with the `src/` folder touched.
- Link the relevant Asana task in the commit when there is one.
- Describe changes plainly, enumerate tests executed (`python3 -m unittest ...`), and attach logs or exports when relevant.
- Commit signing depends on the active workstation. On client machines that use 1Password SSH signing, keep `gpg.format=ssh`, `commit.gpgsign=true`, and `gpg.ssh.program=/Applications/1Password.app/Contents/MacOS/op-ssh-sign`; run `git commit` outside the filesystem sandbox so 1Password can display its biometric authorization prompt. On non-client machines without 1Password, do not require that signer path and do not block normal commits solely because `1Password.app` is unavailable. Before committing, inspect the local Git signing config and use the configured signing flow when it exists; if stale 1Password-only config remains on a non-client machine, remove or update that local config instead of creating a fake signer path.
- Whenever a script is added or adjusted, offer to commit and push the changes.
- If the user accepts that offer, provide the proposed Conventional Commit message(s) and wait for final confirmation of the message(s).
- The user's final confirmation of the proposed commit message(s) authorizes both the commit and push; no further confirmation or verification is required before performing them, unless the user says otherwise.
- Do not create a commit or push until that final commit-message confirmation is received.
- Keep new script shebangs aligned with the interpreter standard (`#!/usr/bin/env python3`).
